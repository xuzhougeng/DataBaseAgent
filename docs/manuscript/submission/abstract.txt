Agent-curated repositories such as scBaseCount show that large language model (LLM) agents can discover, annotate and reprocess public sequencing data at a scale manual curation cannot reach. That demonstration is a single bespoke repository: its agent, pipeline and cloud deployment were engineered for one assay by one institute. Most researchers need something smaller and more specific, and the need takes one of two shapes: a laboratory that already holds a curated table and wants it published as a searchable resource, or a laboratory that must first gather every public dataset on its organism, tissue or perturbation of interest and process it uniformly with tools it trusts. GPSAdb, a manually curated compendium of 3,048 human gene-perturbation RNA-seq datasets, is the authors' own instance of both. Here we present DataBaseAgent (DBA), a general-purpose desktop workbench that turns the agent-curated repository pattern into a tool any researcher can run, in either shape. DBA ships as one binary for Windows, macOS and Linux with no server or database to deploy for the workbench itself. Website construction is driven by the user's goal, the supplied data and a domain skill: the agent inspects the available results, reads a SKILL.md containing domain knowledge and interpretation constraints, and authors the page structure, visualisations and interactions. The current implementation produces a standalone static HTML site with embedded data; fixed table and card templates remain optional. Preview, iteration and download are local, while publication through a configured Model Context Protocol (MCP) provider is a separate action. The broader design includes dynamic websites, but database-backed services for large datasets remain an implementation and evaluation limitation. A collecting project states its topic, organism, assay and inclusion criteria in free text; candidates are gathered from Europe PMC, PubMed or GEO, or imported; an LLM reviewer proposes include, exclude or uncertain with a verbatim evidence snippet that the application verifies against the record, and a dataset enters the repository only through a recorded decision that carries a written reason and names who made it; the user writes the processing pipeline as ordinary shell steps and locks a version; jobs run on the user's own Linux server over SSH under CPU and concurrency quotas, network failures are retried a bounded number of times and everything else is escalated to the user with the log and a resume point; outputs are checksummed, manifested and archived locally. One project agent and four specialists, each with its own model, instructions and fixed tool list, work in a single conversation per project; they act only through the same validated commands as the interface, run only when addressed, and every call, including every MCP call, is recorded. Any OpenAI-compatible, Anthropic or Gemini endpoint, including locally served models, can be the model. We present DBA as a design contribution: its two workflows and architecture, the skill and MCP mechanisms and their boundaries, the safeguards around acting agents, two collection walkthroughs on live services, one of which carries a single GPSAdb-style dataset from a GEO search through a help request to a checksummed count matrix, an Agent-authored PBMC5k website case with 5,025 cells, and a feature comparison with repository-scale curation agents, dataset fetchers, screening tools, workflow platforms and static publishing tools. Usability and the quality of the repositories users build with it remain to be evaluated. Software availability is described in the Data and code availability section.
